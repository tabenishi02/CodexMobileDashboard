# 更新頻度と保存期間

## 基本方針

v0.1.0では、作業用PCの通常収集はWindowsタスクスケジューラから`collect-once --incremental`を定期起動する。既定周期は1分である。各実行は共通mutexを取得し、既存の未送信Snapshotを先に再送してから新規収集・JSON生成・HTTPS送信を行う。

ターン完了時の即時起動と、Codex作業中30秒・停止中60秒へ切り替えるスケジュールはv0.1.0では実装しない。過去履歴の大量AI補完も通常収集から暗黙起動せず、`backfill-ai`を明示操作として分離する。

詳細なタスク登録・状態確認は[`SCHEDULED_EXECUTION.md`](SCHEDULED_EXECUTION.md)を参照する。

## 作業用PCの確認と送信

| 状態 | 動作 | 既定間隔 |
|---|---|---:|
| 通常運用 | 未送信再送 → `collect-once --incremental` | 1分 |
| 送信失敗 | キューへ保持し、次回定期実行で再送 | 1分 |
| AI未処理turn | 共有推論上限を超えた分をpendingへ保持し、次回へ持ち越す | 次回定期実行 |
| 大量の過去補完 | `backfill-ai`で利用者が明示実行 | 自動実行しない |

- JSONLは保存済み読取位置以降を増分処理し、必要な場合だけ安全に先頭再解析する。
- 秘密情報除外後のレコードを識別子と出現位置で重複判定し、同文という理由だけでは削除しない。
- Git変更メタデータは各Collector実行時に取得する。
- collectorと再送専用runnerは同じmutexを使用し、重複起動時は同時処理しない。
- Snapshotは送信前にPC未送信キューへ保存し、Androidのcommit成功確認後だけ削除する。

## スマートフォンの更新

| 状態 | 動作 |
|---|---|
| 画面表示中 | 15秒ごとに更新確認 |
| 別タブ、画面消灯、バックグラウンド | 自動更新停止 |
| 画面へ復帰 | 即時更新後、15秒間隔を再開 |
| 手動操作 | システム情報の更新ボタンで即時更新 |

ETagと`If-None-Match`を使用し、内容が変わっていない場合は`304 Not Modified`を利用する。正常な自動更新では成功メッセージを常設せず、通信失敗や一部取得失敗だけを通知する。

画面にはデータ生成日時、Androidサーバーの最終受信日時、PCの最終確認日時、前回送信成功日時を区別して表示する。

## 保存期間

| データ | 保存方針 |
|---|---|
| Codexセッション履歴 | collector自身では削除しない |
| Git変更メタデータ | 表示用Snapshotとして生成 |
| 通信失敗データ | Androidのcommit成功確認までPCキューに保持 |
| 読取位置・推論台帳 | 自動削除しない |
| PC・Androidの運用ログ | 日単位ローテーション、直近7世代 |
| Androidの公開Snapshot・staging・receipt | `SNAPSHOT_RETENTION.md`の保持方針で安全に定期整理 |

Androidサーバーの受信処理そのものは容量不足時に既存データを勝手に削除せず、新規POST/commitを`507 Insufficient Storage`で拒否する。容量管理は別のSnapshot保持整理タスクがcurrent・PCキュー・直近世代・受信途中データを保護した上で行う。

## 想定される反映時間

PCの定期Collectorが既定1分周期、閲覧ブラウザが表示中15秒周期であるため、新しい完了データの反映時間はCollectorの次回起動、収集・推論・送信時間、ブラウザの次回確認に依存する。1分を超えるAI推論や送信再試行が発生する場合もあるため、固定の最大秒数は保証しない。
