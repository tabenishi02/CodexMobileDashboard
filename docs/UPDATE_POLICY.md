# 更新頻度と保存期間

## 基本方針

Codexのターン完了時は即時更新し、イベントの見落としやCodex以外で行われた変更は定期確認で補う。通常データは内容が変わった場合だけAndroidサーバー端末へ送信し、稼働確認は小さなハートビートで行う。

## 作業用PCの確認と送信

| 状態 | 動作 | 間隔 |
|---|---|---:|
| Codexのターン完了 | 収集、JSON生成、変更時送信 | 即時 |
| Codex作業中 | JSONLの追加部分とGit状態を確認 | 30秒 |
| Codex停止中 | JSONLの追加部分とGit状態を確認 | 60秒 |
| 通常データ | 前回送信内容から変わった場合だけ送信 | 変更時 |
| ハートビート | 直前5分間に正常な送信がない場合に送信 | 5分 |

- JSONLは前回処理位置以降の追加部分だけを読む。
- Gitは最初に`HEAD`と作業ツリー状態を確認し、状態が変わった場合だけ変更メタデータを取得する。
- 定期確認とターン完了処理が重なった場合は、同じデータを重複生成・送信しない。
- Codex作業中に生成した情報には、未確定の途中状態であることを記録する。
- ハートビートには収集ツールの状態、確認日時、最終データ変更日時を含める。通常データを5分以内に送信している場合、別のハートビートは送信しない。

## スマートフォンの更新

| 状態 | 動作 |
|---|---|
| 画面表示中 | 15秒ごとに更新確認 |
| 別タブ、画面消灯、バックグラウンド | 自動更新停止 |
| 画面へ復帰 | 即時更新後、15秒間隔を再開 |
| 手動操作 | 更新ボタンで即時更新 |

ETagと`If-None-Match`を使用し、内容が変わっていない場合は`304 Not Modified`を返してJSON本文を再送しない。

画面には、データ生成日時、Androidサーバー端末の最終受信日時、PCの最終確認日時、最終データ変更日時を区別して表示する。これにより「変更がない状態」と「収集または通信が停止した状態」を判別する。

## 保存期間

| データ | 保存方針 |
|---|---|
| Codexセッション履歴 | 自動削除しない |
| Git変更メタデータ | 関連するセッション履歴とともに保持 |
| 通信失敗データ | Androidサーバー端末が受信成功を返すまでPCに保持 |
| 処理済み位置情報 | 自動削除しない |
| PCとAndroidサーバー端末の運用ログ | 日単位でローテーションし直近7日分 |

- 通信失敗データは送信順序と一意な識別子を保持し、再送による重複保存を防ぐ。
- Androidサーバー端末の空き容量不足時も過去データを自動削除しない。PC側で未送信データを保持し、容量確保後に送信を再開する。
- JSONLが移動した場合はセッションIDで追跡する。ファイルが短縮または置換された場合は保存済み位置を検証し、必要に応じて再解析して重複を除外する。

## 想定される反映時間

ターン完了を正常に検出した場合、PCからAndroidサーバー端末への送信は即時に開始する。スマートフォンが画面表示中なら、通常は送信完了後15秒以内に反映される。

ターン完了を検出できなかった場合も、Codex作業中は最大30秒、停止中は最大60秒でPCが変化を再確認する。これにブラウザの最大15秒の確認待ち時間が加わる。
