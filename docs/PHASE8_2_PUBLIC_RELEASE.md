# Phase 8.2：v0.1.0 公開準備

## 目的

Phase 0～8.1で完成したLAN内HTTPS版のCodex Mobile Dashboardを、初回公開版 `v0.1.0` として安全に公開できる状態へ整える。

Phase 9「外部アクセス」はv0.1.0の対象外とし、本Phase完了後も保留する。v0.1.0ではTailscaleやインターネット経由アクセスを実装しない。

## 基本方針

- Phase 0～8.1の既存実装をv0.1.0の機能範囲とする。
- 既に完了した実機試験や自動テストを理由なく再実施しない。既存証拠をMVP条件へ照合し、不足する確認だけ追加する。
- 公開前にリポジトリの現在内容だけでなくGit履歴も監査する。
- 実設定、Token、秘密鍵、実証明書、ログ、生成データ、個人情報を公開しない。
- 公開用の文書では、開発Phaseより利用者向けの導入・運用・制約を優先して説明する。
- GitHubリポジトリのPublic化とv0.1.0 Release作成は、公開前監査がすべて合格した後に行う。
- Phase 9は削除せず、v0.1.0後の将来拡張として維持する。

## v0.1.0 の機能範囲

v0.1.0は次の状態を初回公開版とする。

- Windows PC上のVSCode Codexセッションを収集・解析する。
- Git変更メタデータを取得する。
- 表示用JSONを生成し、Android・Termuxサーバーへ認証付きHTTPSで送信する。
- Androidサーバーがcommit済みSnapshotだけを公開する。
- スマートフォンのブラウザから公開中workspaceを一覧選択し、作業状況・チャット・エラー・決定事項・変更ファイル・次作業・システム情報を閲覧する。
- 定期収集、未送信再送、障害復旧、recovery/fullバックアップ、Snapshot自動整理を利用できる。
- LAN内HTTPSを正式な通常運用とする。

次はv0.1.0対象外とする。

- Tailscaleまたはインターネット経由の外部アクセス
- スマートフォンからのCodex操作やファイル編集
- PWA、WebSocket、SQLite
- 高度な検索・比較・統計など将来拡張バックログの機能

## 実施順序

### 1. MVP最終判定

`docs/MVP_ACCEPTANCE.md` のMVP-01～MVP-10を、Phase 0～8.1の実装・テスト・実機受入記録へ照合する。

- 既存の証拠で満たす項目は再試験せずPASS根拠を記録する。
- 根拠不足だけ追加確認する。
- `TASKS.md`末尾のMVP完了条件を実績と一致させる。
- 未解決のcritical/error相当不具合がないことを確認する。
- 最終判定結果を文書化する。

### 2. 公開前セキュリティ・プライバシー監査

現在の追跡ファイルとGit履歴の両方を対象に確認する。

主な確認対象：

- API Token、Bearer Token
- 秘密鍵、CA秘密鍵、サーバー秘密鍵
- 実運用の証明書・CSR
- パスワード、環境変数、認証URL
- 実設定INI
- ログ、runtime data、Snapshot、Codex実会話
- 個人名、メールアドレス、ユーザー固有の絶対パス
- 公開不要な実IP、端末固有情報
- その他、第三者へ公開すべきでない情報

問題を検出した場合はPublic化しない。必要ならファイル修正だけでなくGit履歴からも除去し、再監査する。

### 3. OSS公開条件の整備

- CodexMobileDashboard本体のライセンスを決定する。
- ルートへ正式な`LICENSE`を追加する。
- `THIRD_PARTY_NOTICES.md`と`licenses/`を確認し、同梱ライブラリのライセンス表示と矛盾がないことを確認する。
- 必要なら著作権表示・再配布条件をREADMEへ追記する。

### 4. 公開用ドキュメント整理

少なくとも次を確認・更新する。

- `README.md`
  - v0.1.0の機能範囲
  - LAN内HTTPS版であること
  - 動作環境
  - 初回セットアップへの導線
  - 通常運用への導線
  - Phase 9 / Tailscaleが未実装であること
- `TASKS.md`
  - MVP完了状態
  - Phase 8.2完了状態
  - Phase 9保留状態
- `docs/CURRENT_HANDOFF.md`
  - v0.1.0公開後の再開地点
- 必要なセットアップ・運用・障害対応文書
- 実環境固有値や内部向け記述が公開手順として誤解されないこと

ドキュメント全体で、旧仕様・旧Phase状態・現在実装との矛盾がないか確認する。

### 5. CHANGELOGとバージョン確定

- `CHANGELOG.md`の`Unreleased`内容を整理する。
- 初回公開内容を`0.1.0`として確定する。
- リリース日を記録する。
- `Unreleased`セクションは次回変更用として残す。
- README等に固定バージョン番号を記載する場合は、将来の更新運用を考慮する。

### 6. 公開前最終テスト

- Python自動テスト一式を実行する。
- クライアント自動テスト一式を実行する。
- 必要な静的監査・公開監査を実行する。
- Phase 8.1完了後の実機受入結果を再確認する。
- 公開直前の変更で実機動作に影響した場合だけ、影響範囲の実機回帰確認を行う。

### 7. 公開直前監査

Public化直前のcommitを固定し、次を確認する。

- `git status`がcleanである。
- 想定外ファイルが追跡されていない。
- 秘密・個人情報監査がPASSしている。
- LICENSEが存在する。
- READMEからセットアップ可能である。
- CHANGELOGがv0.1.0状態である。
- MVP最終判定がPASSである。
- Phase 9がv0.1.0対象外として明記されている。
- 公開対象commitの自動テストが成功している。

### 8. GitHub公開・v0.1.0 Release

公開前監査合格後に実施する。

- GitHubリポジトリをPrivateからPublicへ変更する。
- `v0.1.0`タグを公開対象commitへ作成する。
- GitHub Release `v0.1.0`を作成する。
- Release Notesへ主要機能、動作環境、LAN内限定、Tailscale未対応、既知の制約を記載する。
- 公開後にREADME・Release・タグ・ライセンス・リポジトリ表示を確認する。

## 完了条件

次をすべて満たした時点でPhase 8.2完了とする。

- MVP-01～MVP-10が正式にPASSしている。
- 公開前セキュリティ・プライバシー監査がPASSしている。
- Git履歴に公開禁止情報が残っていないことを確認している。
- CodexMobileDashboard本体のLICENSEが確定・配置されている。
- README・TASKS・CHANGELOG・主要運用文書がv0.1.0仕様と整合している。
- 公開対象commitで自動テストが成功している。
- GitHubリポジトリがPublicになっている。
- `v0.1.0`タグとGitHub Releaseが公開されている。
- 公開後確認が完了している。
- Phase 9が将来タスクとして保留されている。
